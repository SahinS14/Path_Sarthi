# Trajectory training on the Mac

## Readiness

**The exploratory IO-VNBD dataset is now prepared and the real-data pilot passed.**
It contains 5,491 ten-second windows (4,933 train / 558 validation) from the
provided synchronized pairs; 778 windows were rejected for recording-clock,
reference-label, IMU-gap, or low-speed-initialization reasons. Its contract is
explicitly **provisional**, not a production certification: the sensor mapping is
the documented/legacy hypothesis, phone speed is treated as m/s based on the
paired-channel evidence, and synchronized relative clocks are aligned at zero.
The legacy prepared-v1 directory still contains speed-regression windows and is
deliberately incompatible with this trajectory trainer.

The new pipeline implements preparation, train-only normalization, trajectory
loss, causal covariance prediction, validation against fixed-filter and
constant-speed baselines, checkpoint selection, early stopping and resume.
It does not implement the remaining Android UI, offline-map or GNSS-fusion work.

## Runtime

Use the project directory in your terminal. The current differentiable filter
uses **CPU float64**, not MPS. There is no `--device mps` option in this command.
The earlier scalar speed model remains separate and can use MPS as before.

Verified locally: 43 tests passed. A two-epoch synthetic pipeline test and a
one-epoch-plus-resume test produced identical final weights. This verifies resume
mechanics, not IO-VNBD accuracy. Tiny test epoch timing is not an estimate for the
full dataset. Use the first short real-data run to estimate full training time.

## Commands

The preparation has already been run here. To reproduce it from raw supplied data:

```sh
PYTHONPATH=work/python-deps python3 idr-benchmark/src/create_provisional_contracts.py \
  --audit outputs/data-audit/session-groups-v1.json \
  --out work/datasets/io-vnbd/recording-contracts-provisional-v1.json

PYTHONPATH=work/python-deps python3 idr-benchmark/src/prepare_trajectory.py \
  --contracts work/datasets/io-vnbd/recording-contracts-provisional-v1.json \
  --out work/datasets/io-vnbd/trajectory-provisional-v1 --seconds 10 --stride 10

PYTHONPATH=work/python-deps MPLCONFIGDIR=work/matplotlib python3 idr-benchmark/src/train_trajectory.py \
  --data work/datasets/io-vnbd/trajectory-provisional-v1 --out outputs/trajectory-provisional-v1 --check-only
```

The real-data pilot already completed one epoch using 12 train and four validation
windows. It produced finite loss/checkpoints and adaptive validation RMSE 38.63 m,
versus 38.75 m fixed-filter and 28.30 m constant velocity. This is only a smoke
run; it does not show an improvement and must not be used as a model result.

Start the actual training in a **new** output folder:

```sh
PYTHONPATH=work/python-deps MPLCONFIGDIR=work/matplotlib python3 idr-benchmark/src/train_trajectory.py \
  --data work/datasets/io-vnbd/trajectory-provisional-v1 --out outputs/trajectory-provisional-v1 \
  --epochs 100 --patience 12 --lr 0.0001
```

To resume, repeat the same command with `--resume`. Epochs is the total desired
epoch count, not additional epochs. Resume is from the last completed epoch;
interrupted partial-epoch work is repeated. Code, data, PyTorch version, learning
rate and patience must match. An early-stopped run does not restart just because
the epoch limit increases. Only load checkpoints generated by this trusted local
pipeline: PyTorch optimizer checkpoints are not safe to load from strangers.

Validation of the best saved checkpoint:

```sh
PYTHONPATH=work/python-deps MPLCONFIGDIR=work/matplotlib python3 idr-benchmark/src/train_trajectory.py \
  --data work/datasets/io-vnbd/trajectory-provisional-v1 --evaluate outputs/trajectory-provisional-v1/best.pt \
  --out outputs/trajectory-provisional-v1/evaluation.json
```

Use a new evaluation filename on repeat; reports are not overwritten by evaluation.

## Outputs and interpretation

- `last.pt`: model, optimizer and RNG state at the last completed epoch.
- `best.pt`: checkpoint with the lowest validation macro-drive horizontal RMSE.
- `history.json`: training loss, all three validation scores and epoch duration.
- `best-validation.json`: per-window distance, endpoint error, drift fraction and
  horizontal RMSE for adaptive covariance, fixed covariance and constant velocity.

The supervised loss uses horizontal trajectory displacement. Phone GNSS supplies
initial velocity and heading; vehicle reference positions are labels only. During
each window the filter receives no further GNSS. This is a dead-reckoning training
component, not a complete GNSS fusion model. Short windows must eventually be
supplemented with 30/60-second and distance-based blackout evaluation. A low mean
RMSE does not prove the PS's <10% drift requirement or lane-level accuracy.

Window preparation currently requires reliable moving GNSS initialization and a
fixed mount. Low-speed initialization windows are excluded, not solved. Robust
stationary alignment, mount changes and live GNSS availability remain product
work. No pristine final test split is claimed for previously explored recordings.

## Before the actual training handoff

1. Verify recording contracts with evidence, retaining full-audit session groups.
2. Run preparation and inspect rejected windows and partition coverage.
3. Run a short real-data pilot and review trajectory errors against both baselines.
4. Confirm rate, memory and epoch duration on this Mac, then issue the long command.

The full run uses all 4,933 training and 558 validation windows. On this Mac, the
small pilot was approximately 0.14 seconds per window, so expect roughly 10-15
minutes per full epoch and potentially many hours total. Early stopping can end
it sooner. Do not add the pilot window-limit flags to the full command.
